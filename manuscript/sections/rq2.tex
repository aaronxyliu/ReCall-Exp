\subsection{RQ2: How does ReCall compare with existing recovery methods?}
\label{sec:rq2}

\subsubsection{Experiment design}
We compare ReCall with four baselines on our ground-truth dataset of 35 repositories. Each baseline takes library source code and bundled JavaScript files as input and returns function mappings. We use the source-map-derived ground truth to evaluate recovery performance. The baselines are selected to answer the following four sub-questions.


\paragraph{RQ2.1: How does exhaustive matching compare with ReCall's anchor-guided recovery?}
We construct an \textbf{AST-Match} baseline using ReCall’s normalized AST matcher. The baseline compares every source function with every bundled function within a repository to assess how much can be recovered through normalized AST matching alone. We do not apply model validation to pairs rejected by the AST matcher as in ReCall workflow, because validating this large candidate set would be prohibitively expensive. Although additional validation could improve recovery, it would not correct false positives already accepted by AST matching. As later we will show, these false positives substantially reduce this baseline’s overall precision, limiting the benefit of adding an expensive validation stage.


\paragraph{RQ2.2: How effectively can state-of-the-art code embeddings match source and bundled functions?}
We use \textbf{JCE-0.5B}~\cite{kryvosheieva2025efficient} as a representative code embedding model. It achieves an average score of 78.72\% on the MTEB (Massive Text Embedding Benchmark) Code benchmark, outperforming other models of similar size. We embed all source and bundled functions and compare their vectors using cosine similarity. For each source function, we select the bundled function with the highest similarity score as its counterpart.

\paragraph{RQ2.3: How does ReCall compare with existing function-level web library recovery techniques?}
Two closely related approaches are Debun and D-Bundlr~\cite{xu2026dbundlr}. Debun introduces the POG representation used by ReCall to identify initial matches. Section~\ref{sec:rq1} evaluates POG matching within ReCall, showing that it achieves high precision but produces an anchor set equivalent to only about 13\% of the ground-truth pairs. We therefore focus this comparison on \textbf{D-Bundlr}, which recovers function identities to support security analysis. D-Bundlr fine-tunes GraphCodeBERT with a classification head on original and bundled function snippets. For each bundled function, the classifier predicts an identity from a fixed label set, which we use to construct the corresponding function mapping.

\paragraph{RQ2.4: Can a latest LLM agent recover library functions from a single task instruction?}
Rapid advances in commercial LLM capabilities for software engineering, as highlighted by Salsabil et al.~\cite{salsabil2026whatsurvives}, raise the question of whether a general-purpose agent can match ReCall's specialized recovery workflow. To investigate this question, we evaluate a \textbf{Codex} agent with tool and network access, using GPT-6.2-Sol with high reasoning effort in a fresh Codex CLI 0.169.0 session. The agent receives a single prompt that describes the recovery task, identifies the input files, and requests one-to-one mappings between source and bundled functions.

\subsubsection{Results analysis}

Table~\ref{tab:rq2-baseline-comparison} compares ReCall with the baselines in terms of recovery rate, precision, cross-library misidentification rate (CLMR), and runtime. CLMR measures the proportion of predictions that assign a bundled function to the wrong source library. Overall, ReCall achieved the highest recovery rate (85.79\%), the highest precision (98.69\%), and the lowest CLMR (0.022\%).

Among the baselines, AST-Match achieved the highest recovery rate (62.79\%), but its precision was only 2.64\%, and it had the highest CLMR. When the matcher allows for variable renaming, many functions can have indistinguishable normalized bodies. A match based on the function body alone can therefore identify the wrong counterpart. ReCall uses POG anchors to locate library code within a bundle and relationships among functions to narrow the set of candidate matches. With this additional context, the AST-matching inside the ReCall workflow achieved 99.19\% precision (Table~\ref{tab:rq1-stage}) as a result.

JCE-0.5B achieved a recovery rate of 9.16\% and a precision of 21.51\%, indicating limited effectiveness of function embedding method on the bundled-function recovery task. On the Webpack subset, D-bundlr recovered only 1.3\% of the ground-truth pairs. Its classifier was trained on a limited set of security-related functions, which likely leads to its low recovery rate on a task spanning a broader range of functions. Its precision was 48.44\%, meaning that more than half of its predicted matches were incorrect. Such errors could lead to false alarms if downstream security checks rely on the predicted function identities.

Codex inspected the supplied source and bundled code, identified heuristic fingerprints, and implemented an AST-based matcher that compared each source function with every bundled function. The resulting matcher achieved higher precision than the normalized AST-Match baseline but recovered only 1.71\% of the ground-truth pairs. We also tested a revised prompt that asked Codex to inspect each source function and identify its most likely bundled counterpart. Across multiple attempts, Codex stopped after approximately 10 minutes without completing the task. Its progress reports suggest two possible reasons: Codex estimated that a candidate-by-candidate search would require billions of comparisons across the dataset, and it struggled to identify evidence linking individual source functions to their bundled counterparts.

\section{Approach}
\label{sec:approach}

In this section, we introduce ReCall, which is designed to recover library-function identities from JavaScript bundles collected from websites. We give an overview of the workflow in Section~\ref{sec:approach-overview}, describe how each conmponent of the workflow works in Sections~\ref{sec:pog-anchors}--\ref{sec:semantic-recovery}.


\subsection{Tool overview}
\label{sec:approach-overview}


Figure~\ref{fig:webpage-workflow} presents ReCall's overall workflow. Given JavaScript library source code and intercepted bundled code during runtime,
Recall takes function as the recovery unit, aiming to recover the one-to-one mapping between bundled functions and source functions. Here the function refer to their definition occurrencces. 
Like exising function-level recovery tools, ReCall apply an iterative approach to identify the mapping from a small set, and add determined pairs into the mapping set,
iteratively expanding the mapping set until no more pairs can be added. The key challenge is how to effciently ensure the correctness of the mapping pairs, since one incorrect mapping
may cause further a lot incorrect results (snowball effect). Another key challenge is how to build a proper graph to enable the exploring to achieve high recovery coverage.

For the first challenge, we use a combination of POG fingerprint and LLM-based semantic comparison. For functions containing enough property operations, the POG-fingerprint-based matching is fast and have high accuracy,
for other functions which usually have a small body, we use LLM-based semantic comparison to check whether they are semantically equivalent. 


 ReCall targets the practical problem of recovering library-function identities from JavaScript bundles collected from websites. It uses structural anchors, function relation graphs, and neighborhood-guided semantic recovery to produce a partial one-to-one mapping from bundled function occurrences to reference definitions. The following subsections detail the workflow, structural anchor identification, function relation graph construction, and neighborhood-guided semantic recovery.
Its inputs are website JavaScript and reference code for candidate libraries and versions identified by existing detectors, such as DEBUN~\cite{kim2025debun}; we assume that the corresponding library distributions have been retrieved. ReCall establishes structural anchors, constructs function relation graphs, and iteratively expands the mapping through neighborhood-guided candidate matching.

\paragraph{Structural anchors.}
Matching POG fingerprints provide initial correspondences from which recovery can expand. Small functions account for \textbf{[TBD\%]} of library functions \textbf{[citation pending]}, but often lack distinctive property-operation structure. ReCall therefore uses POG matches as starting points and retains small functions for semantic matching.

\paragraph{Function relations and neighborhood exploration.}
Relations among functions provide context for locating additional correspondences. ReCall constructs graphs for the reference and bundled code, accounting for relationships obscured by bundler transformations. Accepted pairs guide exploration of corresponding neighborhoods, restricting the comparison space instead of comparing every reference function with every bundled function.

\paragraph{AST comparison and candidate ranking.}
ReCall first checks normalized ASTs to avoid model requests for directly matching candidates. If this check fails, embedding similarity prioritizes a small set of structurally supported candidates for LLM validation. These stages reduce the number of expensive semantic comparisons.

\paragraph{Semantic validation and iterative expansion.}
The LLM compares function bodies despite renaming and expression rewriting, supporting recovery where POG evidence is sparse. Small bodies keep comparison inputs compact. To avoid gathering extensive enclosing code, the comparison assumes correspondences between external bindings without verifying their definitions; this can introduce mismatches. Accepted pairs extend the mapping and provide new starting points for neighborhood exploration, continuing until no further matches are found or a configured limit is reached.

\subsection{Structural anchor identification}
\label{sec:pog-anchors}

\paragraph{Function inventories.}
We extract reference and bundled function inventories $S$ and $B$ from the input files $F_s$ and $F_b$, including anonymous and nested definitions. Each bundled identity retains its file/hash and function span; each reference identity additionally retains its package/version candidate. Ambiguous versions remain candidates, and missing references limit recovery. Reference distributions need not be upstream development source. Source maps and evaluation counterpart labels are excluded from recovery. The completed model experiments supply known references and therefore evaluate recovery rather than upstream detection or retrieval; their settings are stated separately from the current defaults.

ReCall initializes recovery with structurally distinctive function pairs. We use the DEBUN POG backend introduced in Section~\ref{sec:background-prior-work} to extract fingerprints~\cite{kim2025debun}. The function inventories retain definitions that are ineligible for anchoring, so the initial mapping does not determine the full recovery scope.

The size criterion for POG anchoring counts syntactic property-operation occurrences in a function's own body. Member reads, writes, and object-literal property initializations contribute to the count; a compound assignment or update contributes one read/write occurrence. For example, \texttt{x.value = y.value} contributes two occurrences. Repeated operations count repeatedly. Parameter defaults and nested function bodies are excluded, and unresolved computed property names use a common placeholder. This count differs from the number of distinct properties or graph nodes.

Nested bodies are removed or replaced by empty function expressions before extraction. An extraction failure cannot establish an anchor. A pair can become an anchor when both functions have at least ten property-operation occurrences, their POG fingerprints agree, and the fingerprint identifies a unique eligible reference within its library scope. Multiple bundled occurrences can share the fingerprint. In the default workflow, ReCall considers anchor pairs in their generated order and accepts a pair only when both function IDs are unallocated across all supplied chunks and library scopes. The accepted pairs form $M_0$.

The size threshold restricts anchoring to functions with more structural evidence, while reference uniqueness excludes ambiguous reference fingerprints within a library scope. Neither condition proves identity. Functions below the threshold remain in the recovery inventory and can be matched during expansion.

\subsection{Function relation graph construction}
\label{sec:graph-construction}
ReCall constructs $G_s=(S,E_s)$ and $G_b=(B,E_b)$ independently to locate candidate counterparts around accepted matches. A function relation graph has function definitions as nodes and typed edges $E\subseteq V\times\mathcal{R}\times V$, where $\mathcal{R}$ contains the six relations in Table~\ref{tab:function-relations}. Multiple relation types may connect the same pair. Neighborhood exploration uses the undirected projection, while subsequent filtering retains relation types and directions.

\begin{table}[htbp]
\caption{Function relations for an edge $f\rightarrow g$. Examples illustrate individual relations; a fragment may induce several types. Callback association records argument passing, not a verified callback invocation.}
\label{tab:function-relations}
\centering\scriptsize
\setlength{\tabcolsep}{3pt}
\begin{tabular}{@{}p{.15\linewidth}p{.24\linewidth}p{.35\linewidth}p{.19\linewidth}@{}}
\toprule
Relation & Definition & Example & Search purpose\\
\midrule
Call & $f$ calls a modeled target $g$. & \texttt{function f(x) \{ return g(x); \}} & Connect callers and helpers.\\
\addlinespace
Function argument & $f$ passes $g$ to a call. & \texttt{function f(xs) \{ return xs.map(g); \}} & Locate supplied callbacks.\\
\addlinespace
Callback association & A call to $f$ receives $g$ as an argument. & \texttt{f(items, g);} & Connect receivers and callbacks.\\
\addlinespace
Function reference & A binding reference in $f$ resolves to $g$. & \texttt{function f() \{ return g; \}} & Capture non-call uses.\\
\addlinespace
Lexical containment & $g$ is directly nested in $f$. & \texttt{function f() \{ function g() \{\} \}} & Locate nested helpers.\\
\addlinespace
Source-order proximity & $g$ follows $f$ within a bounded same-parent window. & \texttt{function f() \{\}}\newline\texttt{function g() \{\}} & Supply nearby candidates.\\
\bottomrule
\end{tabular}
\end{table}

The first four relations capture explicit uses of function values, including higher-order interactions. Containment and proximity provide complementary search connections when use relationships cannot be resolved. We select relations that directly connect recovery targets and can be extracted statically from both inputs without website execution. Proximity is limited to definitions at most two positions apart under the same immediate parent and input unit; connecting all functions in a file or module would create much broader neighborhoods. Statement-level control/data dependence would require a finer-grained analysis, while dynamic relations would depend on exercised website behavior. The selected relations are search evidence: neither their preservation through bundling nor their sufficiency for recovery is assumed. Reference edges remain within a library scope; bundled edges may cross supplied chunks.

Graph construction resolves function values through the available lexical and module context, emits function-use relations, and adds containment and proximity edges. Appendix~\ref{sec:graph-details} gives the construction algorithm and implementation details.

\paragraph{Available context and runtime scope.}
\label{sec:local-context}
Context collection is independent of target selection. A supplied runtime helper can explain an export operation even if the helper itself is not a matching target. Starting from the files listed in each input manifest, the collector follows relative ESM imports and reexports, literal dynamic imports, local CommonJS requests, and statically specified module URLs only within declared local roots. It records missing files and unresolved requests. Computed chunk loading requires the relevant files to be supplied explicitly. The collector does not execute bundle code.

Module identities are scoped by environment and loader or registry. Equal numeric IDs in independent runtimes must not merge. Explicit annotations and supported worker-entry forms establish these scopes; unknown scope information remains a limitation of the input. Context code supplies constraints, while function-node emission is projected to the chosen matching inventory. This distinction lets runtime initialization/export code assist recovery without first matching its initialization functions.

\paragraph{Resolving relationships across module boundaries.}
Building on D-Bundlr's module-analysis decomposition~\cite{xu2026dbundlr}, ReCall recognizes runtime structures, binds factory parameters to module operations, and resolves imported values. These operations produce relationships for candidate search.

In the running example, the reference import binds \texttt{normalize} to its definition. On the bundled side, \texttt{load(7)} selects the scoped module record, and the getter for \texttt{k} transfers the function token for \texttt{q} to that record's export property. Resolving \texttt{n.k(...)} consequently exposes the relationship from \texttt{a} to \texttt{q}. Module registration alone would not resolve this function-level connection.

Adapters represent each factory by a module record scoped to its loader or registry. Assignments, imports, exports, and export getters propagate function values through a shared representation of lexical bindings and object properties. This makes the resolved relation available to recovery without requiring a match for the runtime helper itself. Appendix~\ref{sec:graph-details} lists the modeled operations.

The common solver propagates aliases, object fields, selected class members, imports, exports, and small return summaries. The summaries specialize direct parameter returns, constant member paths from parameters, and returned function/class values at individual call sites. They handle common identity and interop helpers without propagating every argument through every application function. Relationships are emitted for uniquely modeled callable values, with function-valued arguments and binding references recorded separately and opaque native alternatives retained. Flow-insensitive and accessor approximations can add neighbors. This is an incomplete candidate graph, not an exact or sound JavaScript call graph.

\paragraph{Bundler-aware resolution.}
\label{sec:bundler-adapters}
Adapters normalize loading and export protocols by structural roles rather than fixed variable names. They handle factory registries and loaders in webpack/Rspack, Turbopack, and Parcel, and lexical links, ESM imports, and retained interop helpers in scope-hoisted output from esbuild, Rollup, and related bundlers. Rolldown's lazy factories and shared helpers also feed the common value model. The resolver follows surviving bindings without reconstructing erased module boundaries. Section~\ref{sec:bundler-selection} explains the selection of bundler families; Appendix~\ref{sec:graph-details} describes their mechanisms and analysis bounds.

\subsection{Neighborhood-guided semantic recovery}
\label{sec:semantic-recovery}
Starting from $M_0$, ReCall repeatedly explores candidates around accepted pairs, compares candidate bodies, and integrates new matches. This restricts semantic comparison to structurally supported candidates rather than the full Cartesian product $S\times B$. Algorithm~\ref{alg:recovery} summarizes the procedure.

\subsubsection{Neighborhood candidate exploration}
\label{sec:neighborhoods}
Let $M$ be the current set of accepted pairs $(b,s)$, with bundled occurrence $b$ and reference function $s$. Let $N_s$ and $N_b$ denote undirected one-hop neighborhoods. The underlying graphs retain edge kinds and directions for the later filter. Source-order proximity links definitions at most two positions apart under the same immediate parent, with top-level functions grouped by file. Source relationships stay within a reference library scope. Bundled relationships can cross supplied chunks by default.

For an available reference $s$, let $R_B$ be the bundled occurrences reserved by pending model proposals in the current round. The structural candidate pool is
\begin{equation}
\label{eq:candidate-neighborhood}
C_M(s)=\left(\bigcup_{(b',s')\in M,\ s'\in N_s(s)}N_b(b')\right)
\setminus\bigl(\operatorname{dom}(M)\cup R_B\bigr).
\end{equation}
A reference is available when it has neither an accepted match nor a pending proposal. The union admits a candidate when at least one accepted pair supports the neighborhood connection. A reference with no matched neighbor has an empty pool. Turning off cross-chunk expansion restricts each candidate to the chunk of its supporting bundled neighbor.

In Figure~\ref{fig:recovery-example}, \texttt{normalize} neighbors the matched reference \texttt{render}. Its bundled counterpart \texttt{a} neighbors \texttt{q} and \texttt{r}, which enter the candidate pool if available. The AST check can pair \texttt{normalize} with \texttt{q} directly. If import or export resolution loses the relevant edge, this search may fail to expose \texttt{q}.

\subsubsection{Semantic candidate matching}
\paragraph{AST comparison and relationship filtering.}
ReCall compares normalized ASTs in bundled inventory order before computing embeddings. Normalization minifies both bodies and permits consistent renaming of local and external identifiers. External binding identities are unverified. The first AST match claims both endpoints and can support later visits in the same round. When AST finds no match, ReCall keeps a candidate only if an accepted pair supports the same relationship kind and direction on both sides.

\paragraph{Reference representation and candidate ranking.}
ReCall minifies each reference function $s$ to obtain $m(s)$, reducing syntactic differences before embedding while retaining the original body for validation. External names remain unchanged because enclosing declarations are unavailable. Isolated minification is a comparison aid rather than a reconstruction of the full bundling context.

ReCall embeds $m(s)$ using the semantic-comparison instruction in Appendix~\ref{sec:prompt}. Bundled functions are embedded as code only. Cosine similarity ranks the filtered bundled candidates, with bundled inventory order breaking ties. The default has no similarity cutoff. At most $k$ candidates proceed to model validation per visit ($k=3$ by default). Embeddings are computed on demand and reused.

\paragraph{Semantic matching under assumed binding correspondence.}
The LLM receives the complete reference function $s$, its minified representation $m(s)$, and the candidate bundled function $b$. It receives no enclosing declarations, captured initializers, neighboring function bodies, or evaluation labels. This avoids collecting and comparing potentially extensive enclosing code for each candidate. Structural context restricts candidate selection, but external binding definitions are absent from the model input.

Let $\operatorname{FV}(f)$ denote the external identifiers referenced by a function $f$. The comparison permits a hypothesized correspondence
\begin{equation}
\rho:\operatorname{FV}(s)\rightharpoonup\operatorname{FV}(b),
\end{equation}
inferred from scope and computational roles in the bodies. A correspondence $\rho(x)=y$ assumes that the external bindings play corresponding roles; it does not establish that their definitions or runtime values agree. The prompt also asks the model to align parameters and local variables. For example, the bodies
\begin{lstlisting}[basicstyle=\ttfamily\small]
function s(x) { return transform(x, options); }
function b(n) { return r(n, o); }
\end{lstlisting}
permit the hypotheses $\texttt{transform}\mapsto\texttt{r}$ and $\texttt{options}\mapsto\texttt{o}$. Their computations correspond under these assumptions, but their actual behaviors may differ if the external bindings implement different operations or supply different values. This is an illustrative binding assumption, not a verified identity match.

We distinguish the model's acceptance judgment from semantic equivalence. For model configuration $\theta$ and comparison policy $P$, define
\begin{equation}
\label{eq:model-acceptance}
A_{\theta,P}(s,b)=\begin{cases}1,&\operatorname{LLM}_{\theta}(P;s,m(s),b)=\texttt{T},\\0,&\text{otherwise}.\end{cases}
\end{equation}
The policy permits inferred external-binding renaming and asks the model to compare computations despite compact JavaScript rewrites. The implementation returns only \texttt{T} or \texttt{F}; it neither extracts nor independently verifies $\rho$. Acceptance is a heuristic judgment, not a proof of equivalence in the original execution environments or of reference identity. In particular, the adopted prompt rejects only on clear evidence of a difference and explicitly excludes corner cases and side effects. Appendix~\ref{sec:prompt} preserves the prompt and historical requests.

The missing binding context can admit wrong identities despite similar bodies. In the completed 27B pilot, eight of the 14 wrong identities involve differing external regex/replacement helpers or data stores (Section~\ref{sec:limitations}); this observation is specific to that experiment. In the running example, the visible \texttt{toLowerCase}/\texttt{toUpperCase} difference instead provides local evidence against confusing the two helpers. The shown counterpart also admits the preliminary AST path; the example does not assert that an LLM call is necessary for that pair. Appendix~\ref{sec:recovery-implementation} records representation, request, and resource settings.

\subsubsection{Iterative recovery expansion}
Model validation follows rank order and stops at the first \texttt{T}. A positive proposal reserves both endpoints for the remainder of the round. At round end, ReCall promotes proposals that pass allocation checks. Later rounds can revisit a reference when the candidate pool or supporting matches change. ReCall skips processed search states and caches exact model requests with their model digest and request settings.

\begin{algorithm}[htbp]
\caption{Default source-first one-to-one recovery}
\label{alg:recovery}
\begin{algorithmic}[1]
\Require Reference functions $S$, bundled functions $B$, graphs $G_s,G_b$, initial anchors $M_0$
\Ensure Partial one-to-one mapping $M$ across all supplied chunks and library scopes
\State $M\gets M_0$
\Repeat
  \State $P\gets\emptyset$, $M_{\mathrm{start}}\gets M$
  \ForAll{eligible available references $s$ in library and inventory order}
    \State Compute $C_M(s)$ using Equation~\ref{eq:candidate-neighborhood}
    \If{the candidate pool is nonempty and the state is new}
      \If{an AST match exists in the pool}
        \State Add the first AST match $(b,s)$ immediately to $M$
      \Else
        \State Filter by edge kind and direction, then rank by cosine similarity
        \State Validate up to three candidates in rank order
        \State On the first \texttt{T}, reserve both IDs and add the pair to $P$
      \EndIf
    \EndIf
  \EndFor
  \State Promote proposals in $P$ that pass allocation checks into $M$
\Until{$M=M_{\mathrm{start}}$ or a configured limit is reached}
\State \Return $M$
\end{algorithmic}
\end{algorithm}

The same one-to-one rule applies to POG, AST, and model matches. Each source inventory ID and bundled function ID can appear in at most one accepted pair across the run. This restriction can leave genuine repeated copies unresolved. An incorrect early match can also claim an endpoint needed by a correct pair and can supply misleading neighborhoods. Accepted matches remain in the mapping.

Each nonterminal round adds at least one pair to a finite inventory. A fixed point records that the procedure found no further matches under its search and acceptance rules. Recovery artifacts record the accepted pairs, their method and supporting matches, and any unresolved bundled functions.

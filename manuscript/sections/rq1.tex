\subsection{RQ1: How does ReCall perform across applications, bundlers, and libraries?}
\label{sec:rq1}

We ran ReCall with its default settings on all 35 repositories in our ground-truth dataset. For each repository, ReCall takes the library source code and the JavaScript files captured at runtime as input and returns a partial one-to-one mapping from bundled functions to library source definitions. We count a match as correct when the reported source location agrees with the ground truth for that bundled function.

We assess recovery performance using precision and recovery rate. Precision measures the fraction of output mappings that are correct, while recovery rate measures the fraction of ground-truth pairs recovered. As shown in Table~\ref{tab:rq1-bundler-breakdown}, ReCall achieved strong recovery performance across all seven bundlers. Across the full dataset, ReCall correctly recovered 49,867 of 58,128 ground-truth pairs, achieving an overall 85.79\% recovery rate and 98.69\% precision. This combination is important for practical use: recovered mappings must be accurate enough to support subsequent analysis while covering as much of the bundled library code as possible. The full experiment took 14 hours and 38 minutes, averaging 1.06 seconds per correctly recovered function.

ReCall first uses POG matching to identify an initial set of function correspondences. The ``Initial Anchor (\%)'' column in Table~\ref{tab:rq1-bundler-breakdown} compares the size of this set with the number of ground-truth function pairs. The overall ratio is only 13.21\%, highlighting the need for subsequent recovery stages to identify functions that POG matching cannot resolve.

Table~\ref{tab:rq1-stage} reports the separate performance and time cost of four stages: POG matching, AST matching, neighborhood ranking, and model validation. Model validation accounts for 89.71\% of the total process time, making it the primary runtime bottleneck. Outside these stages, function relationship graph construction accounts for an estimated 4.88\%, and other processing accounts for 0.48\%.

For matching and validation, an accepted function pair is a positive prediction, and the ground-truth mapping determines whether it is correct. Each stage is evaluated on the pairs it examines, so the confusion matrices describe stage-specific decisions rather than a shared set of comparisons. All three stages achieve high precision. However, POG matching misses approximately 30\% of the correct pairs, and AST matching rejects approximately 25\% of the correct pairs it examines. These unresolved pairs are left for semantic checking in the later stage.


Neighborhood ranking selects up to three candidates for model validation. Its recall measures how often the correct counterpart appears among these candidates. We count a query as a true positive when the correct counterpart is included and as a false negative when it is not. In approximately 15\% of assessed queries, the correct counterpart falls outside the selected candidates and therefore does not reach model validation in that query. Model validation produces 373 false positives and 1,421 false negatives, representing incorrect acceptances and rejections, respectively. To investigate these errors, we modify the prompt to request an explanation of each decision and group the resulting explanations into the categories shown in Table~\ref{tab:rq1-rejection-reasons}.

\subsection{RQ1: How does ReCall perform across applications, bundlers, and libraries?}
\label{sec:rq1}


We ran ReCall with its default settings on all 35 repositories in our ground-truth dataset. For each repository, ReCall takes the library source code and the JavaScript files captured at runtime as input and returns a partial one-to-one mapping from bundled functions to library source definitions. We count a match as correct when the reported source location agrees with the ground truth for that bundled function.

\subsubsection{Performance Evaluation}

We assess recovery performance using precision and recovery rate. Precision measures the fraction of output mappings that are correct, while recovery rate measures the fraction of ground-truth pairs recovered. As shown in Table~\ref{tab:rq1-bundler-breakdown}, ReCall spent 14 hours and 38 minutes, averaging 1.06 seconds per function, to finish the recovery, and achieved strong recovery performance across all seven bundlers. Across the full dataset, ReCall correctly recovered 49,867 of 58,128 ground-truth pairs, achieving an overall 85.79\% recovery rate and 98.69\% precision. This combination is important for practical use: recovered mappings must be accurate enough to support subsequent analysis while covering as much of the bundled library code as possible. For the functions that we failed to recovery, we randomly pick some libraries and do manually code inspection, we find that if our model validation can correctly judge every function pairs, the improvement is still limited. The major problem lies in there are some separate files of library, have no function relationship with other recovered ones and no big function meet POG size requierment to become an anchor. So our anchor based exploration algorihtm fail to reach them.

ReCall first uses POG matching to identify an initial set of function correspondences. The ``Initial Anchor (\%)'' column in Table~\ref{tab:rq1-bundler-breakdown} compares the size of this set with the number of ground-truth function pairs. The overall ratio is only 13.21\%, highlighting the need for subsequent recovery stages to identify functions that POG matching cannot resolve.

Table~\ref{tab:rq1-stage} reports the separate performance and time cost of four stages: POG matching, AST matching, neighborhood ranking, and model validation. Model validation accounts for 89.71\% of the total process time, making it the primary runtime bottleneck. Outside these stages, function relationship graph construction accounts for an estimated 4.88\%, and other processing accounts for 0.48\%.

For matching and validation, an accepted function pair is a positive prediction, and the ground-truth mapping determines whether it is correct. Each stage is evaluated on the pairs it examines, so the confusion matrices describe stage-specific decisions rather than a shared set of comparisons. All three stages achieve high precision. However, POG matching misses approximately 30\% of the correct pairs, and AST matching rejects approximately 25\% of the correct pairs it examines. These unresolved pairs are left for semantic checking in the later stage.


Neighborhood ranking selects up to three candidates for model validation. We use define recall as how often the correct counterpart appears among these candidates. We count a query as a true positive when the correct counterpart is included and as a false negative when it is not. In approximately 15\% of assessed queries, the correct counterpart falls outside the selected candidates and therefore does not reach model validation in that query. Model validation produces 373 false positives and 1,421 false negatives, representing incorrect acceptances and rejections, respectively. 

\subsubsection{Failure Analysis}
Table~\ref{tab:rq1-stage} reveals limitations at different stages of recovery. POG and AST matching rely on structural features that bundling can alter, causing them to miss some valid correspondences. Neighborhood ranking can also miss correct counterparts when embedding similarity does not adequately capture the relationship between the original and transformed code. To investigate model validation errors, we modify the prompt to request explanations of the model's decisions, manually inspect the affected function pairs, and classify the reasons into the categories shown in Table~\ref{tab:rq1-rejection-reasons}.

As shown in Table~\ref{tab:rq1-rejection-reasons}, all false positives fall into the external bindings category: the model treats references to different external bindings as identifier renaming. For example, \texttt{return encodeURIComponent(x)} and \texttt{return escape(x)} have the same local structure but call functions with different behavior. Because ReCall validates function bodies without their surrounding context, the model cannot resolve external references to their definitions and may incorrectly accept such pairs. These errors account for less than 4\% of validated pairs, suggesting that function-body-only validation offers a practical tradeoff between accuracy and analysis cost. Resolving external bindings through additional context or pointer analysis could reduce these errors, but would introduce complexity and overhead.

False negatives in Table~\ref{tab:rq1-rejection-reasons} reflect several difficulties in recognizing valid transformations. Despite explicit instructions to allow consistent renaming of external bindings and omission of build-only branches, the model still rejects some pairs that differ only in these permitted ways. More complex transformations, such as restructuring conditional branches, make it difficult for the model to determine whether different control-flow structures preserve the same behavior.

To assess how much stage-level errors limit recovery, we conduct a ground-truth-guided simulation that assumes perfect precision and recall for decisions within the four stages, while retaining ReCall's anchor eligibility and exploration rules. Under these conditions, recovery increases from 85.79\% to approximately 89\%. This limited improvement indicates that decision accuracy alone does not explain the remaining recovery gap.

We further investigate this gap by selecting low-recovery-rate libraries with unrecovered functions and manually inspecting their code. A major obstacle we found is that some library files have neither a function that meets the POG anchor-size requirement nor a function relationship connecting them to an already recovered function. These files provide no starting point or entry path for anchor-based exploration. Consequently, their functions remain unreachable even when the subsequent matching and validation decisions are correct.

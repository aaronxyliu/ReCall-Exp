\subsection{RQ1: How does ReCall perform across applications, bundlers, and libraries?}
\label{sec:rq1}



\subsubsection{Data Collection}
\label{sec:data-collection}

We evaluate ReCall on web applications with source code publicly available on GitHub. Access to their source code and build configurations allows us to obtain library sources and generate source maps for establishing ground-truth correspondences between source and bundled functions.

We select seven widely used bundlers based on the bundler usage survey\footnote{\label{fn:bundler-usage-survey}State of JS build-tools survey: \url{https://2025.stateofjs.com/en-US/libraries/build-tools/}}: Webpack, Vite, esbuild, Rollup, Turbopack, Parcel, and Bun. For each bundler, we search GitHub for applications that use it and examine repositories in descending order of star count. We require each application to have a frontend page that builds and opens successfully and at least five production library dependencies. This process yields 35 repositories.

We construct the ground-truth dataset by collecting library source code, runtime intercepted JavaScript files, and source maps from each repository. We identify production libraries from project configuration files and randomly select up to ten per repository, yielding 282 library instances from 35 repositories. We manually enable source-map generation and verify that each application’s frontend opens successfully. Following prior work (CITE LATER), we capture JavaScript files loaded when the home page opens and retrieve their source maps from the build output. Our collection does not cover additional files whose loading requires page interactions.

Before establishing ground-truth mappings, we need to first discuss four special function transformations introduced by the build process that affect recovery: removal, addition, combination, and splitting. Removal eliminates source functions, for example through tree shaking, while addition introduces functions such as generated helpers or functions produced by factories. Removed functions are absent from the bundle, and added functions have no original source counterpart to recover. Recovery is therefore not meaningful in either case, and we exclude both from the recovery evaluation.

Combination and splitting can preserve program behavior while breaking the function-level semantic equivalence on which ReCall relies. To assess their impact on ReCall’s applicability, we estimate the frequency of them using source-map relationship: one-to-many correspondences indicate splitting, many-to-one correspondences indicate combination, and source functions without any mapped bundled counterpart indicate removal. We omit addition because generated library functions are difficult to distinguish from application code.

Our source-map analysis shows that one-to-one correspondences dominate the observed category counts across the 35 repositories. We identify 1,835 split candidates (2.49\%), 1,319 combine candidates (1.79\%), and 12,438 remove candidates (16.87\%), alongside 58,128 one-to-one function pairs (78.85\%). The relatively small shares of split and combine candidates suggest that boundary-changing transformations have a limited impact on ReCall’s applicability within this dataset. As a result, we can safely construct the ground-truth dataset using only one-to-one mappings, assuming that each bundled function has exactly one correct source-function counterpart in our experiments and vice versa.

Table~\ref{tab:rq1-stage-accuracy} reports assessed precision as $\mathrm{TP}/(\mathrm{TP}+\mathrm{FP})$ and stage recall as $\mathrm{TP}/(\mathrm{TP}+\mathrm{FN})$. POG recall uses the 9,454 ground-truth pairs in which both functions have a POG fingerprint and at least ten own-body property-operation occurrences. Of these, 7,212 had equal fingerprints, 6,738 appeared in the raw anchor list, and 6,643 were retained by one-to-one allocation. POG uses fingerprint lookup and produces no explicit negative comparisons, so its TN count is undefined under this protocol.

AST and Qwen counts use distinct examined pairs within each repository. AST counts come from a local replay that logged every AST comparison and reproduced the final recovery trace using archived model responses. Qwen counts use pairs with binary verdicts in that trace. A pair examined more than once within a stage counts as positive if that stage accepted it. Stage recall uses only ground-truth-positive pairs eligible for POG, examined by AST, or given a binary Qwen verdict, respectively. A pair may enter more than one stage denominator. Ground-truth-unassessed pairs are excluded from the table.

\subsubsection{Completed evidence: jQuery model recovery}
These completed results use the known-version jQuery fixture and original local graph (Section~\ref{sec:model-fixture}). All three builds reach a fixed point.

The reference distribution contains 558 static definitions: 85 (15.23\%) have at least ten own-body property-operation occurrences, 393 have one to nine, and 80 have none. These are implementation instances, not distinct implementation patterns. Eligibility alone does not establish a stable or unique fingerprint.

Table~\ref{tab:exp4-recovery} separates initial POG matches from final recovery. The builds contain 568, 568, and 577 total function definitions, respectively. Of these, 545, 544, and 540 have supported jQuery identities and form the recovery denominators. Matching nevertheless retains all definitions, including application and runtime code.

Initial POG matching supplies 85, 77, and 76 correct anchors. Expansion adds 429, 427, and 444 correct matches. Final recovery ranges from 92.65\% to 96.30\%. The descriptive pooled result is 1538/1629 supported bundled-function occurrences (94.41\%), including 1300 correct matches beyond the 238 initial POG correspondences. There are 14 wrong identities and 45 unassessed promotions. Repeated occurrences across builds are correlated. Across configurations, 541 distinct reference identities are correctly recovered; this uses the 558-definition reference inventory as its denominator and must not be confused with bundled-target recovery.

\paragraph{Validation and final identity accuracy.}

\input{data/exp4-validation}

Table~\ref{tab:exp4-validation} distinguishes precision among assessable accepted pairs from precision of final matches. The procedure performs 2962 pair checks using 2286 distinct fresh requests and 676 exact-request cache hits. All responses satisfy the T/F contract; no API error or thinking text is recorded. Among 1485 accepted checks, 1363 agree with supported reference identities, 77 disagree, and 45 are unassessed. Assessed accepted-pair precision is 1363/1440 (94.65\%), rather than 1363/1485. Repeated checks are not independent trials.

Across attempted assessable pairs, there are 1363 true positives, 68 false negatives, 77 false positives, and 1363 true negatives under the identity-label policy. These counts concern candidates actually examined, not arbitrary function pairs. Final assessed identity precision is 1538/(1538+14), or 99.10\%. Initial POG matches, repeated-query outcomes, and one-to-one filtering explain why pair and final-match denominators differ; a positive judgment alone is not the final output.

Top-five recall is conditional on attempted queries with a supported counterpart. A function may contribute several queries as its matched neighborhood changes. Of the 1300 correct model-promoted matches, 1104 were accepted at rank one, 132 at rank two, 36 at rank three, 12 at rank four, and 16 at rank five. Thus, 28 correct promotions occur at ranks four or five in their saved queries. This is an observed distribution, not an isolated estimate of the gain from increasing the validation budget.

Table~\ref{tab:exp4-barriers} assigns an exclusive outcome to each of the 91 supported targets not correctly recovered. Wrong promotion takes precedence; the other outcomes inspect all saved queries. The largest categories are explicit rejection of a correct top-five pair (21), an accepted correct pair blocked by a reference-identity conflict (17), a correct candidate never entering the top five (16), and early acceptance preventing validation of a correct top-five candidate (15). \subsubsection{Preliminary multi-repository evidence: anchor coverage and recovery}
\label{sec:rq1-anchor-coverage}
We examine whether initial anchor coverage is associated with recovery in a snapshot of the ongoing top-three experiment. At 13:56 China time on 8 November 2026, 22 of the 26 repositories had completed recovery. This run uses module-aware neighborhoods, AST comparison followed by Qwen3.5:27b validation of up to three ranked candidates, and no embedding-similarity cutoff. Accepted matches initialize subsequent rounds, and a source identity may match multiple bundled targets. For 21 repositories, the run incrementally continues saved top-three results after the method-parsing and source-resolution fixes, retaining prior accepted matches; it is not a fresh run of a single revised configuration. The subsequent local graph-syntax repairs are not included in this snapshot. These results are preliminary and separate from the jQuery pilot above.

The observation unit is a repository--library instance, so the same package in different repositories contributes separate observations. We exclude instances with no initial anchor or fewer than 20 ground-truth (GT) pairs, retaining 84 instances. For comparability, the anchor count includes only GT-evaluable bundled targets assigned an initial POG match, whether that identity is correct or incorrect; unassessed anchors are excluded. Let $G$ be the number of GT pairs, $A$ the number of initially anchored GT targets, $C$ the number of correctly recovered pairs, and $C_A$ the number of correct anchors. Initial anchor percentage is $A/G$, and overall recovery is $C/G$. To remove the direct contribution of anchors to recovery, we also measure recovery among initially unanchored targets as $(C-C_A)/(G-A)$.

Figure~\ref{fig:rq1-anchor-recovery} shows a positive association between anchor percentage and recovery. Mean overall recovery increases from 59.4\% in the 0--5\% anchor range (26 instances) to 77.5\% in the 5--10\% range (21 instances), and 83.2\% in the 10--15\% range (14 instances). The corresponding non-anchor recovery rates are 58.1\%, 75.7\%, and 81.1\%. Across the 84 instances, Spearman's rank correlation is 0.53 between anchor percentage and overall recovery and 0.47 between anchor percentage and non-anchor recovery. In contrast, the correlation between absolute anchor count and overall recovery is 0.19. Thus, the association is stronger for relative anchor coverage than for anchor count alone and persists after removing the direct contribution of anchors.

These observations are consistent with initial anchor coverage affecting the opportunity for propagation, but do not establish that unrecovered functions lack relationships with existing anchors. Missing graph edges, candidate ranking, and validation decisions can also limit recovery, while code that readily yields anchors may also be easier to recover. Repeated packages across repositories are not independent observations. Each range above 20\% anchor coverage contains only one to three instances, so its mean should not be interpreted as a stable trend. Direct reachability analysis and controlled anchor ablations are needed to distinguish these explanations.

\subsubsection{Planned experiment 1: different bundlers}
\label{sec:rq1-bundlers}
We will apply the complete method, including the extended relationship graphs, to local repository builds produced by different bundlers. The verification cohort will be held out from configuration selection, with references and input conditions fixed in advance. We will report recovery, assessed precision, wrong and unassessed mappings, runtime, and model calls per bundler, with macro summaries and pooled counts. Where the same subject can be built with multiple bundlers, we will retain paired comparisons; comparisons between different applications will be described as cohort differences rather than isolated bundler effects. Failure analysis will distinguish absent matched neighbors, missing or poorly ranked candidates, model decisions, and allocation conflicts.

\subsubsection{Planned experiment 2: different libraries and frameworks}
\label{sec:rq1-libraries}
Using local builds and exact versioned references, we will evaluate different libraries and frameworks and report the same recovery and cost measures per target package. Package selection and the inclusion of framework runtimes will be declared before observing results. The framework-runtime exclusions in the completed graph cohorts remain part of those historical cohorts; they do not constitute completed framework recovery evidence. The planned evaluation will retain reference sizes, supported target counts, parse failures, and unresolved cases, and distinguish previously used subjects from held-out subjects. We will report POG size eligibility and admitted anchors separately; the planned eligibility measurement in Background remains unfilled.

\subsubsection{Planned experiment 3: function transformations and recovery rate}
\label{sec:boundary-characterization}
Section~\ref{sec:data-collection} reports the initial split, combine, and no-counterpart screen on the new capture dataset. We will manually validate flagged candidates before drawing conclusions about compiler transformation frequency. For each selected library and build, we will relate source definitions to the bundled functions receiving their mapping points. Nested bodies will be attributed to their innermost functions. We will retain all contributor votes rather than only the dominant identity used by the recovery oracle. The current screen retains point-supported contributor edges and requires two distinct original positions for accepted one-to-one pairs. Follow-up validation will examine sensitivity to stronger edge-support thresholds. Relations will be aggregated across the supplied chunks of one build; independent builds will remain separate.

\paragraph{Manual validation.}
Review will inspect the exact source and generated code, mapping locations, and enclosing contexts. Multi-target cases will be checked for genuine partitioning versus duplicated copies or nesting artifacts; multi-source cases will be checked for combined contributions, including inlining. For no-target cases, reviewers will also inspect generated top-level regions and all supplied chunks, using build-input inventories and compiler evidence where available. A missing function definition after inlining will count as combination when its computation survives, rather than as removal. Removal requires evidence that the function's computation was eliminated. Cases without sufficient evidence will remain unresolved. Each decision will retain source/generated locations, supporting evidence, and review notes, with disagreements adjudicated explicitly. These labels will be independent of ReCall's predictions.

\paragraph{Counts and recovery consequences.}
We will report screened candidates, confirmed transformations, alternative explanations, and unresolved cases per library and bundler. Counts will identify affected source definitions per build, with bundled-function and transformation-group counts reported separately. Overlapping transformations will be marked explicitly rather than summed into an exclusive partition. The source-inventory scope, parsing failures, missing artifacts, and map coverage will accompany each denominator. Final conclusions will distinguish observed frequency from unresolved coverage and relate validated cases to ReCall's outcomes: recovery and assessed precision for surviving supported counterparts, and coverage limits where no standalone counterpart remains. Confirmed removals will be reported as build elimination rather than matcher failures. The existing supported-target recovery denominator will remain explicit; the characterization will not silently convert unsupported transformations into assessed matches or exclude them from the scope discussion.

For each library/build case, we will relate its confirmed split, combine, and remove frequencies to its library recovery rate, retaining unresolved transformation cases separately. We will compare cases within bundler and library groups where the data permit and report target counts, source-inventory coverage, and anchor coverage alongside the association. This analysis will describe relationships rather than establish that transformations alone cause differences in recovery. Rates over surviving supported targets and coverage relative to the source inventory will remain separate, since removal or loss of a standalone boundary can change the available target population.
